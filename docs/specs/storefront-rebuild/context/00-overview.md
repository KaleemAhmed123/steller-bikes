## In plain words (read this first)

**The shop.** Raju Cycles is a real bicycle shop in Kanpur, UP. The owner wants an online store
where customers browse cycles and place orders, plus a private back-office ("admin") where the owner
and staff manage products, stock, and orders.

**Why a rebuild.** A first version (v1) already exists, generated by the OpenAI "Sites" platform. It
works, but it's locked to Cloudflare's platform, written in an unreadable compressed style, and has
no real customer login. The owner — who knows the React + Node ecosystem — chose to **rebuild on a
stack they can maintain** and carry over v1's proven design. Full v1 audit:
`C:\Users\hp\Desktop\raju-cycles\AUDIT-REPORT.md`.

**What "maintainable" buys us.** The single biggest factor for a small shop is: *can a normal
developer read and change this later?* That is why we picked a conventional, boring stack over a
clever one, and why ponytail (build the least that works) governs every choice.

## The one idea that explains the whole system

**The server is the authority on price and stock. The admin is permission-gated. Build the least
that works.**

Everything follows from that:
- **The browser is never trusted.** It can send "I want 2 of variant X with coupon Y", but the
  **server** looks up the real price, the real stock, the real coupon, and computes the total. A
  tampered client cannot change what it pays.
- **Stock can't oversell and checkout can't double-charge.** Those two paths use a database
  transaction plus a guard (details in [`01-domain-and-data.md`](01-domain-and-data.md)). This is
  the one genuinely hard part and the main thing we port from v1.
- **Every admin action checks a permission first.** Staff see only what their role allows.
- **If a feature isn't needed for the MVP, it isn't built yet.** Scope is a phase list, not a
  big-bang.

## The stack (and why each piece earns its place)

| Layer | Tech | Why it's here (one line) |
|-------|------|--------------------------|
| Storefront + admin UI | **Next.js (App Router) + TypeScript** *(frontend only)* | Routing + SSR (server-side rendering, for SEO) out of the box. Frontend only — it never touches the DB; it fetches from the Express API. *(Updated at build step 2; see D9.)* |
| Styling | **Ported v1 CSS theme** (charcoal + lime), plain CSS | v1's hand-written theme is good and portable; no heavy component library (ponytail). |
| API | **Node + Express + TypeScript** | The conventional, well-understood backend; any Node dev can maintain it. |
| Database | **MongoDB (Atlas)** | Owner's choice. Atlas free tier is a replica set, so multi-document **transactions** work — which we need for safe checkout. |
| DB access | **Mongoose** (proposed) | Schema + validation in one place; familiar. (Open question — see [`02-decisions.md`](02-decisions.md).) |
| Validation | **Zod** | Reject bad input at the API boundary; the one trust boundary we never cut. |
| Auth v1 | **Email+password for staff, cookie cart for guests** | Covers a local shop's real MVP need; full customer accounts deferred. |

> **Anti-goal: technology soup.** If a dependency or layer can't answer "why am I here" in one line,
> it's cut. The v1 audit found ~48 unused UI components and ~12 dead dependencies — we do not repeat
> that.

## Architecture (target, in text)

```
CUSTOMER (browser)                          OWNER / STAFF (browser)
      │                                           │
      ▼                                           ▼
   Next.js frontend (Vercel)  ── App Router, SSR for SEO; no DB access ──
      │                                           │
      │  server-render fetch (no CORS)   +   browser fetch (needs CORS)
      ▼                                           ▼
            Express API (Render)  (one app, validated at the edge with Zod)
      │   auth check · guest cookie · permission check · recompute totals
      ▼
   Domain logic:  catalog · cart · checkout(tx) · orders · inventory · settings
      │
      ▼
   MongoDB (Atlas replica set)   ──  transactions for checkout + stock
```

- **Frontend and backend are separate apps on separate hosts** (Next.js on Vercel, Express on
  Render). The frontend renders and fetches; **Express stays the authority** on price/stock. Because
  they're different origins, the browser's calls need **CORS** (a backend allow-list for the
  frontend's domain). *(Updated at build step 2; see D9–D10.)*
- **One backend app**, not microservices (ponytail — a shop doesn't need them).
- **Checkout is the one transactional path**: create the order, decrement stock with a guard, all or
  nothing.
- Later phases bolt on: Razorpay (online payment), returns, promotions, CMS pages, media, full
  staff roles, audit log — each behind the same API, added when needed.

## What is NOT in the MVP (later phases)

Online card payments (Razorpay) · returns/refunds · promotions/coupons UI · CMS pages & campaigns ·
media library · full staff-role management UI · audit trail UI · customer accounts & order history ·
courier booking · email/SMS notifications. Each is a known later phase, not a gap we forgot.

## Glossary

- **Storefront** — the public shop pages (browse, product, cart, checkout).
- **Admin / back-office** — the private pages where the owner/staff run the shop.
- **Variant** — one buyable version of a product (a size/colour of a cycle) with its own price,
  SKU, and stock.
- **SKU** (Stock Keeping Unit) — the unique code for one variant; what stock is counted against.
- **Guest checkout** — buying without making an account; the cart is tied to a browser cookie.
- **COD** (Cash On Delivery) — the customer pays cash when the cycle is delivered.
- **Paise** — 1 rupee = 100 paise. We store money as whole paise (integers) to avoid rounding bugs.
- **Transaction** — a group of database writes that all succeed or all fail together; how we stop
  overselling and double-charging.
- **Idempotency key** — a one-time id the browser sends with a checkout so the same submit twice
  makes only one order.
- **Fulfillment state** — where an order is in its life: confirmed → processing → packed → shipped →
  delivered (plus cancelled / delivery-failed).
